01 // Ficha Técnica del Laboratorio

Nombre del Laboratorio: File path traversal, simple case

Clasificación OWASP: A01:2021 – Broken Access Control

Tipo de Explotación: Unsanitised Input / Direct Path Traversal

Objetivo Técnico: Exfiltrar el archivo /etc/passwd del servidor subyacente manipulando la ruta de carga de imágenes en la aplicación web.

02 // Marco Teórico y Fundamentación Técnica

¿Qué es File Path Traversal?
La vulnerabilidad de File Path Traversal (también conocida como Directory Traversal) se presenta cuando una aplicación web utiliza parámetros o entradas provistas por el usuario para construir rutas de acceso a archivos alojados en el servidor, sin realizar una sanitización o validación estricta de dichos datos.


Mecanismo de Explotación (Secuencia Dot-Dot-Slash):
Los sistemas operativos basados en POSIX (Linux/Unix) y Windows utilizan la secuencia especial ../ (o ..\) para indicar una navegación hacia el directorio padre (subir un nivel). Cuando una aplicación web no filtra estas secuencias, un atacante puede "escapar" del directorio raíz donde opera la aplicación web (ej. /var/www/images/) y escalar libremente por el sistema de archivos del servidor.


Impacto en la Triada de Seguridad (CIA):

  • Confidencialidad (Violación Crítica): Un atacante puede leer archivos arbitrarios del sistema, como códigos fuente, archivos de configuración con credenciales de BD (.env, web.config), o claves privadas SSH y contraseñas (/etc/passwd, /etc/shadow).
  • Integridad: En combinaciones con otras vulnerabilidades o si existen permisos mal configurados de escritura, podría permitir la modificación de archivos del sistema.
  • Disponibilidad: Permite leer archivos de dispositivos especiales (ej. /dev/zero en Linux), lo que podría agotar los recursos de memoria y causar una denegación de servicio (DoS).

03 // Procedimiento de Explotación Paso a Paso

A continuación se detalla la metodología técnica utilizada para resolver el laboratorio mediante el uso de Burp Suite Community Edition:

  1. Intercepción y Reconocimiento:
    Iniciamos el navegador integrado de Burp Suite y accedimos a la URL del laboratorio. Al explorar la tienda virtual, observamos que las imágenes de los productos son cargadas dinámicamente mediante una solicitud HTTP con la estructura: 
    GET /image?filename=29.jpg HTTP/1.1
  2. Captura del Tráfico HTTP:
    En Burp Suite, nos dirigimos a la pestaña Proxy > HTTP history, identificamos la petición dirigida al endpoint /image, hacemos clic derecho y la enviamos a la herramienta Repeater (Ctrl + R).
  3. Construcción e Inyección del Payload:
    En la pestaña Repeater, modificamos el valor del parámetro filename. Sabiendo que el servidor corre en Linux y que el archivo de imágenes está en una subcarpeta profunda, inyectamos la secuencia de escape: 
    GET /image?filename=../../../etc/passwd HTTP/1.1
  4. Ejecución y Exfiltración:
    Hacemos clic en el botón Send. El servidor responde con un código de estado HTTP/2 200 OK y devuelve en el cuerpo de la respuesta (Body) la lista completa de usuarios del sistema contenidos en el archivo /etc/passwd.
  5. Confirmación:
    Refrescamos el navegador principal para confirmar que la plataforma de PortSwigger registra el laboratorio como resuelto ("Lab Solved").

05 // Análisis Técnico del Payload

Payload empleado: ../../../etc/passwd


  • ../ : Retrocede un nivel en el árbol de directorios del servidor. Si la imagen original se lee desde /var/www/images/29.jpg, el primer ../ nos posiciona en /var/www/, el segundo en /var/ y el tercero en la raíz del sistema de archivos /.
  • etc/passwd : Apunta a la ruta absoluta del archivo de configuración del sistema Linux donde se almacenan las cuentas de usuario, sus UID, GID y shell predeterminada.

06 // Estrategias de Mitigación Recomendadas

Para corregir y prevenir esta vulnerabilidad en entornos de producción se deben aplicar las siguientes buenas prácticas:

  • Evitar pasar rutas provistas por el usuario: En lugar de recibir nombres de archivo directa o indirectamente en la URL, utilizar identificadores numéricos o índices mapeados en una base de datos segura (ej. /image?id=12).
  • Sanitización e Identificación por Lista Blanca (Whitelist): Validar que el valor del parámetro contenga estrictamente caracteres alfanuméricos y extensiones de imagen válidas (ej. ^[a-zA-0-9]+\.(png|jpg)$), rechazando cualquier intento con slashes o secuencias ../.
  • Uso de APIs Canónicas de Archivos: Verificar mediante código de servidor que la ruta absoluta resuelta pertenezca al directorio base permitido antes de servir el archivo: 
    // Ejemplo de verificación en Java
File file = new File(BASE_DIRECTORY, userInput);
if (!file.getCanonicalPath().startsWith(BASE_DIRECTORY)) {
    throw new SecurityException("Acceso no autorizado fuera del directorio base.");
}
